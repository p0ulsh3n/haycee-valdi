# Profile composition

The app Profile tab places `ProfileScreenHeader` over the cover with no fixed “Profil” title. Support, share and preferences SVG actions stay at the right. As the user scrolls past their identity, the header changes to a white surface and reveals the avatar/name with a short transition. The icons have no individual backplates and use the existing navigation assets.

`ProfileCover` is the shared banner used by both the signed-in Profile tab and `SellerProfileScreen`. It supports a color-panel fallback, an optional cover image, the seller-style bottom shade and an optional overlay for storefront delivery details. `layout.profile` owns the cover and overlapping avatar geometry.

`ProfileIdentitySection` is shared by the signed-in Profile tab and `SellerProfileScreen`. It owns the display name, username, optional location, stats row and bio. Each screen keeps its own profile avatar and feature tabs. Place the identity section before the profile's shared `SwipeTabs` so seller and regular-user profile content follow the same hierarchy.

The first tab of the signed-in profile is `Mon compte`. `ProfileAccountMenu` presents Wallet with an optional FCFA balance, Mes commandes, Assistance Live, Centre de notifications, Paiement and Livraison. It uses existing navigation SVGs and an optional unread badge, with no dividers between rows. Wallet opens its own account screen. The other five rows open `ProfileAccountDestinationScreen`: orders show local demo orders with colored image panels, functional status filters and French long dates formatted by `formatFrenchLongDate`; selecting an order opens `ProfileOrderDetailScreen`, which shows its line items, quantities, option labels, prices, payment and delivery details, totals, and status timeline. Its seller row shows the boutique avatar and name and opens `SellerProfileScreen`. Prices, seller profiles and order metadata remain in `profile/data/ProfileOrdersDemoData.ts`. Notifications have a truthful empty state, Live Support contains expandable quick answers, Payment explains that payment choices are shown during checkout, and Shipping lets the user view or select a pickup point through the shared `AddressPickerSheet`. Account and support services are not connected yet.

The Wallet row opens `WalletScreen`, which starts with a full-width, unboxed summary on the standard white page surface, followed by account KPIs and payment rows. The summary presents available balance and pending payments together, with a lime availability caption and centered Retirer and Recharger shortcuts. Retirer opens `WalletWithdrawalScreen`; Recharger currently gives availability feedback until an account-wallet funding flow is connected. The actions use the shared CTA and outline button variants with existing navigation SVGs. The available balance uses primary text color, not CTA color. Balance amounts use the shared `priceLarge` scale with width-aware reduction for long FCFA values. KPI cards use a narrower left column and a wider right column so FCFA values can keep the same value size as the order counts. Each KPI separates its title, brand-accent period/status label, primary value and muted explanatory caption; change indicators are omitted until real comparison data exists. The withdrawal screen validates the amount against the displayed available balance and minimum before enabling the withdrawal CTA. Dashboard figures and the masked payout account are local presentation fixtures in `profile/data/WalletDemoData.ts`; withdrawal submission does not move funds until a wallet service is connected.

The profile tab uses the existing `SwipeTabs` component and design-system tokens. Until account data and destinations are connected, its profile values, zero counts and empty tab messages are presentation placeholders; the header action callbacks are supplied by the owning screen.
